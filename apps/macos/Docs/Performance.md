# 执行核心的性能边界

更新日期：2026-09-25。

现已同时具备 `RequestmanCore` 的通用执行基础和 `RequestmanProxy` 的 HTTP/1.1 真实流式转发、基础动作、全局记录界面。两者的限制范围如下，不能将独立核心测试当作代理已使用全部能力。Chrome/Surge 链路和端到端性能尚未实测。


## 本轮实际代理路径

NIO 单事件循环拥有全部连接状态，默认只监听 127.0.0.1。宿主仅负责启动、配置快照和每 200 ms 消费记录；网络循环不等待主线程或磁盘。SwiftNIO handler 上的 `@unchecked Sendable` 只用于事件循环约束内的 peer 回调，不能跨 loop 访问这些状态。

| 项目 | 当前限制与行为 |
| --- | --- |
| 连接 | 最多 64 个（包括 CONNECT 隧道）；满后关闭新连接并生成容量失败记录；没有无界任务或等待队列 |
| 读取 | 关闭 autoRead；单 socket read 16 KiB、每轮一次；对端写完成后才读取下一块 |
| 建连前预读 | 最多 64 KiB、128 个 HTTP part；超过后失败 |
| Header | 每个字段和整个列表最多 32 KiB，解析最多 128 个字段；修改后重新校验列表大小 |
| 步骤 | 每个方向最多 64 个；首个流程匹配；Mock/请求重定向终止请求方向，然后执行响应方向 |
| 生成内容 | 单模板/解析值最多 1 MiB；并发连接生成 Body 的逻辑载荷共享 16 MiB 额度，关闭连接后释放 |
| 时限 | 建连 5 秒、HTTP 总事务 30 秒；CONNECT 建立后每端读空闲 120 秒关闭 |
| 待显示记录 | 最多 256 条，每次消费最多 64 条；溢出淘汰旧记录，界面显示丢失数量 |
| 界面历史 | 最多 500 条，5 Hz 批量追加；用稳定 UUID 和原生 Table；筛选仅覆盖此窗口 |
| 记录字段 | URL 最多 2,048 字符；每方向最多 40 个 Header，每字段值最多 256 字符；步骤最多 64 条；截断标记与脱敏字段名随记录保留 |
| Body 快照 | 原始/最终请求与响应各最多 64 KiB；在途、待显示和历史快照共享 32 MiB 逻辑载荷预算，预算不足仅截断预览 |
| 详情解析 | 选中记录后台按需解码 gzip/deflate；每层输出最多 256 KiB、最多 8 层编码；JSON 最多 256 KiB、64 层、每侧 4,096 节点 |
| 配置 I/O | 350 ms 防抖，独立 actor 串行 JSON 原子写；退出前刷盘，失败保留提示 |

网络转发不聚合完整 Body、不解压、不解析；通过有界采集器保留前缀，固定替换只替换发送内容并消费原流。生成内容额度计入原生字符串的 UTF-8 载荷，NIO 输出缓冲、String 分配、操作系统 socket buffer 仍有额外开销，不能等同于进程 RSS 上限。报文长度和分块由代理重建。快照共享不可变存储，预算租约随最后一个所有者释放；达到首个缺口后不再追加后续字节。完整空体与未采集、断流、截断分开记录。

解码、JSON 差异和源码字符串不计入网络快照预算，只为当前选中记录已访问的两个 Body Tab 构造，切换记录取消任务并释放旧数据；因此不是进程 RSS 上限。类型变化不把不兼容的子项强行配对，搜索不裁剪节点的复制内容。

基础静态动作没有异步等待，直接运行于事件循环，不通过下文的 `FlowExecutionRuntime` 叠加排队。完整 Body/JSON、脚本、辅助请求接入时才需要将异步 runtime 的资源生命周期与 transport 结合；不能在这个事件循环执行任意脚本或磁盘操作。

HTTP 当前每连接一个事务，没有连接池；TLS 可解密或透传，取决于证书配置。尚未做吞吐和 p95/p99 基准，因此 64/16 MiB/5 Hz 是保守初始边界，不是调优结论。长流、连接复用和规则索引仍是后续性能工作。

## 通用执行基础组件

| 组件 | 已实现行为 |
| --- | --- |
| [FlowExecutionPlan](../Packages/RequestmanCore/Sources/RequestmanCore/FlowExecutionPlan.swift) | 不可变计划与环境版本；根据节点输入需求，分别确定请求和响应的 Body 处理模式 |
| [BoundedExecutionGate](../Packages/RequestmanCore/Sources/RequestmanCore/BoundedExecutionGate.swift) | 并发上限、有界 FIFO 等待、队列满明确拒绝、等待取消、完成/失败释放名额 |
| [BodyPreparation](../Packages/RequestmanCore/Sources/RequestmanCore/BodyPreparation.swift) | 拉取式读取、逐块预留预算、单 Body 上限、全局共享预算、取消和错误释放、缓冲对象共享 |
| [ExecutionEventBuffer](../Packages/RequestmanCore/Sources/RequestmanCore/ExecutionEventBuffer.swift) | 固定容量元数据环形缓冲、限制单次取出数量、溢出淘汰最旧事件并报告缺失数量 |
| [FlowExecutionRuntime](../Packages/RequestmanCore/Sources/RequestmanCore/FlowExecutionRuntime.swift) | 将上述组件串联成一次请求/响应操作的生命周期，执行时限覆盖排队与运行 |

核心不依赖 UI，不把 `CaptureService` 的 `@MainActor` 扩展为执行线程。异步执行入口使用 `@concurrent`；状态同步只使用 macOS 14 可用的短时锁，不在锁内运行用户动作、磁盘操作或 UI 回调。

## 默认资源限制

以下仅用于 `FlowExecutionRuntime`，与上文 NIO 代理实际限制分开。它们可通过 `ExecutionLimits` 配置，不是实测最优参数或吞吐承诺。

| 参数 | 初始值 | 范围 |
| --- | --- | --- |
| 活跃实例 | 16 | 一份 runtime，覆盖其管理的全部项目 |
| 等待实例 | 32 | FIFO；满后抛出 `queueFull`，不绕过流程 |
| 单 Body 载荷 | 4 MiB | 需要完整读取的请求或响应 Body |
| 累计缓冲载荷 | 64 MiB | 包含仍被持有的 Body 和正在读取的预留字节 |
| 单次读取 | 64 KiB | 读取器必须遵守上限并支持取消 |
| 记录事件 | 2,048 条 | 固定大小生命周期元数据，不包含 URL、Body 或脚本输出 |
| 单次记录批次 | 128 条 | 一个下游消费者负责取出，再提供存储/UI 查询 |
| 执行时限 | 30 秒 | 从提交计时；调用方可传入更早的绝对截止时间 |

不能为每条请求新建 runtime，否则全局容量失效。未来脚本和辅助请求应有独立额度，不能复用被等待它们的主请求占满的执行队列。

## 接入契约

### 计划与 Body

在配置保存/切换时生成不可变计划和环境快照。输入需求需要包含所有可能执行分支：只改 Header 或固定替换 Body 不需要读取原 Body；动态转换原 Body 则必须声明 `completeBody`。当前实现只接收输入需求，不分析脚本或编译完整流程。

一次 `execute` 的闭包覆盖双向处理和实际发送；不能只启动一个后台转发任务就提前返回。请求和响应各调用一次 `prepareBody`，共享其结果供节点读取：

- `streaming`：原样交还读取器，不调用 `read`、解析 JSON 或复制 Body。后续转发仍由传输层负责背压。
- `buffered`：按需拉取，读前预留容量；超限明确失败，不静默透传未经修改的数据。
- 小碎片合并为有上限的分块，避免逐字节输入产生数百万个记录对象。
- `BufferedBody` 在最后一个所有者释放时归还载荷预算，可供多个逻辑视图共用。
- 分阶段只准备一次；执行结束的上下文不能继续发起新的 Body 读取。

`BodyReader` 必须遵守分块上限，空块非法，EOF 返回 `nil`，不在内部无界预读。若需要修改压缩 Body，传输适配器应提供解码后字节，使上限应用于解码后载荷；解压器自身也必须有工作内存和输出限制。

累计预算是逻辑载荷限制，不是进程 RSS 限制。它不包含 Data 分配余量、块索引、解压工作区、JSON/JS 对象及消费者另行复制的数据。调用方使用块时必须持有 `BufferedBody`；独立复制、变换输出或落盘缓存需要另外记账，不能取出 Data 后释放所有者以规避预算。

读取 EOF 也需要少量预留空间；容量接近满载时可能保守拒绝下一次读取，即使下一次原本会返回 EOF。不要把单 Body 限额设置成恰好占满全局预算。后续可通过传输层可靠的结束标记优化这一点，不能信任未经核对的 Content-Length。

### 取消和截止时间

截止时间覆盖排队、读取、辅助等待与发送。排队取消移除等待者；运行中取消传播给操作；成功、异常和取消都归还活跃名额。

当前超时使用结构化并发，取消是协作式的：传输读取器和注入操作必须响应取消。若它们忽略取消，runtime 会等待其退出，不能宣称在截止时间硬终止。原生代码不得把不受控的 JS 死循环放入执行闭包；脚本硬终止需要隔离工作进程，尚未实现。客户端取消也需要未来的传输适配器接入。

仅在真正持有并处理流量时使用主请求名额；不要为项目/文件夹串行化所有请求。项目层级用于组织，不是调度锁。

### 记录与界面

转发路径只追加固定大小的生命周期事件，不等待数据库提交或 UI 刷新。慢消费者导致环形缓冲淘汰最旧事件，下一次 `drain` 返回缺失数量；消费者必须展示/保存记录不完整状态，不能把它当作可靠审计日志或完整当前状态源。

`drain` 是单消费者接口，不能让数据库和 UI 各自取走一部分事件。未来记录服务分批写入后，向 UI 提供摘要分页和所选实例详情。当前代理通过另一条 `CaptureRecordBuffer` 通道批量接入 UI；此固定事件环尚未消费到数据库，也没有完整节点输入输出追踪。

暂停记录必须与停止流程分开。后续列表应按稳定 ID 增量更新，历史记录分页读取；Body 格式化和差异计算仅对选中内容后台按需执行。UI 不是网络处理的必要参与者。

## 测试与尚待验证

通过 `swift test --package-path apps/macos/Packages/RequestmanCore` 验证核心行为：

- Header-only/无 Body 需求不调用读取器，请求与响应需求独立。
- 恰好达到单 Body 上限可成功，超限/非法块/取消释放预算。
- 跨实例的缓冲所有者仍计入共享预算；释放后可再次使用。
- FIFO、队列溢出、等待取消、运行错误、截止时间及上下文结束行为。
- 环境快照不随原始字典修改而变化。
- 没有记录消费者时执行继续完成，缓冲和单批大小有界，缺失数量可见。

未运行 App；已有本地回环真实 socket 集成测试，但没有 Chrome、吞吐或端到端延迟测量。后续在受控服务下比较直连、仅代理和启用流程，分别测量未命中、Header-only、大 JSON/压缩 Body、Token 获取、断点和全局记录场景。报告 p50/p95/p99、峰值内存、队列长度、记录丢失及取消后的资源回落；将辅助请求/人工等待与自身计算时间分开。

剩余实现包括：HTTP/2 流控、TLS 连接复用、JS 与辅助 HTTP 请求及其缓存/独立额度、磁盘/数据库容量、完整大 Body 的按需存储、匹配索引、模板预解析和完整 JSON 转换预算。
